# Design

A pristine fork server is a separate freshly executed interpreter started before customer traffic. It never receives customer payloads or results; only its forked child unpickles the trusted host-supplied process arguments. Child results use bounded JSON bytes, never pickle. Customer plugin imports occur after child privilege drop. The supervisor/template run as root inside the disposable container; customer code runs as UID/GID 65532 with no capabilities. The only added container capabilities are SETUID, SETGID and KILL for this supervisor. No host mounts, network, Docker socket or host secrets reach containers.

A naive fork of the request-handling process is not an acceptable template: it can inherit old request/result memory. The selected fork-server topology avoids this. Linux UID separation, a private root-owned multiprocessing directory and closed child descriptors protect supervision channels. Tests must verify those assumptions and retain failures. This is defense in depth inside a shared container, not a formal hostile-code sandbox certification.

Matrix: all existing residue cases plus module/default/cache/hook state, descriptor leaks, signal/umask state, forged stdout, supervisor access, memory exhaustion and timeout. Performance: pool sizes 1/2/4/8/16 where headroom permits; small/64KiB/256KiB payloads; short CPU, memory and simulated I/O; fixed arrivals, bursts, heavy/short mixture; repeated longer validation at promising operating points and a 30-minute soak. Tests run sequentially with node headroom guards, bounded queues, operation deadlines, exact-name cleanup and live evidence checkpoints. Test size can be reduced on a real resource/quality boundary; a failed case remains evidence.

Additional coordinator diagnostic: hold four warmed native workers constant while increasing dormant customer registrations. This separates registry-scan cost from worker/startup cost and is explicitly not a many-customer throughput claim. If measured, replace full registry scans in dispatch with lifecycle-maintained active/resident indexes; preserve admission/fairness/cleanup semantics and verify source and packed consumers.

Transport comparison uses the Docker Engine local Unix attach API with bounded demultiplexing and identical inspected container settings. No Docker socket enters a plugin. The legacy density recorder is made sparse so few-call customers do not each preallocate six large histograms; merged percentiles and allocation are checked. Additional full-host Python/TypeScript/C# fixed-arrival controls remain separate from the reuse prototype.

Actual-host low-frequency tests exposed false busy results while a pending pristine startup occupied the last reservation. A controlled ready-handshake gate reproduces the defect before the fix. Foreground acquisition now takes priority over refill, waits on per-worker shared-startup completion within its existing deadline, and rechecks compatible readiness after the launch semaphore. Default direct admission remains fail-fast; cancellation must not destroy an unacquired shared startup. Source and packed tests cover compatible/incompatible profiles, cancellation and independence from unrelated startup. The production observer also includes owned CLI instance names for unbound/pristine workers. Production controls are rerun after this fix before final soak.

The extended matrix reaches 128 Engine containers only after full-reservation headroom validation with a further 2-GiB margin. A real System V shared-memory leak across child replacements led to external IPC auditing and container retirement. A separate 100-ms child-exit deadline produced false failures at 64-way load; a shared response/exit deadline and deterministic delayed-exit controls correct it. All failed pilots remain evidence.

Final population controls compare 4/8-GiB budgets over two once-per-minute calls per customer. A marginal 256-customer latency failure prompted four additional counterbalanced controls with new seeds. Neither budget passes every 256-customer repetition, so the report retains the lower confirmed population instead of selecting only favorable runs. Memory increases help retain a complete 128-customer working set but do not establish a monotonic throughput improvement under customer churn.
